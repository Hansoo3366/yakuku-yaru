# 배포 스크립트가 중간에 조용히 끝남

## 증상

- 운영 API가 죽은 채로(502/504) 배포 workflow가 **성공**으로 끝남.
- 배포 로그가 `nginx: configuration file ... test is successful` 줄에서 멈춤. 그 뒤의 `caddy validate`, health 체크, 이미지 정리, ghcr 로그아웃 출력이 없음.
- IAP 방식으로 바꾼 6e881f1부터 da93bb0 직전까지 배포 5번이 모두 같음. 즉 health 체크가 **한 번도 실행되지 않았음**.

## 원인

배포 스크립트를 stdin으로 보내 `bash -s`로 실행했다.

```bash
{ printf '%s\n' "$GHCR_TOKEN"; cat scripts/deploy/remote-deploy.sh; } | ssh ... "bash -c 'read -r GHCR_TOKEN && exec bash -s'"
```

`bash -s`는 스크립트를 stdin에서 한 줄씩 읽으며 실행한다. 그런데 스크립트 안의 `docker compose exec -T gateway nginx -t`도 stdin을 읽는다. 이 명령이 **아직 실행되지 않은 나머지 스크립트를 입력으로 삼켜 버려서**, bash는 EOF를 만나 exit 0으로 끝났다.

## 재현

`exec` 때 stdin을 전부 읽는 가짜 `docker`를 PATH 앞에 두고 옛 스크립트를 같은 방식으로 실행하면, `nginx -t` 직후 exit 0으로 끝난다.

## 해결 (da93bb0)

1. 본문 전체를 `main()` 함수로 감싸고 마지막 줄에서 `main "$@" < /dev/null`로 실행. bash가 함수를 끝까지 읽은 뒤 실행하고, 안의 명령은 stdin을 읽을 수 없다.
2. 마지막에 `DEPLOY_OK <SHA>`를 출력하고, workflow는 `grep -qx "DEPLOY_OK $GITHUB_SHA"`로 이 줄이 있어야 성공 처리.
3. 새 컨테이너 직접 확인: api·web이 `running`, `RestartCount` 0, `Config.Image`가 이번 이미지인지. 20초 뒤 한 번 더.
4. `trap ... EXIT`로 실패해도 ghcr 로그아웃.

이후 715ec08에서 스크립트를 stdin으로 보내지 않고, 서버의 `yakuku-deploy`가 디스크의 파일을 실행하도록 바꿨다. → [[IAP 터널과 배포 전용 사용자]]

## 교훈

- 배포 스크립트의 "성공"은 끝까지 실행됐다는 증거가 아니다. 마지막 표시(`DEPLOY_OK`)를 확인한다.
- stdin으로 스크립트를 넘길 때, 안의 명령(`docker exec`, `ssh`, `read` 등)이 stdin을 읽는지 본다.
- health 체크는 gateway를 거치면 이전 컨테이너나 캐시가 답할 수 있다. 새 컨테이너 자체를 확인한다.
