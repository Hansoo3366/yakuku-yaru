# 회고

## 잘 된 점

### 도메인과 학습 요구사항의 결합

게시판·CRUD만 만드는 과제가 아니라, **야구 팬이 실제로 쓸 만한 캘린더·직관 기록**으로 확장했다. 과제 체크리스트와 제품 경험이 동시에 채워진다.

### KBO 데이터 파이프라인

공식 API가 없는 제약 안에서 일정·선발·라인업·순위를 **cron + 파서**로 안정화했다. `pending` ID → 실제 `gameId` 갱신 패턴은 외부 데이터 동기화의 좋은 연습이었다.

### 배포 현실 대응

e2-small에서 서버 빌드가 터지는 문제를 **GHCR 빌드 분리**로 해결했다. 학습 프로젝트에서도 "작은 VM" 제약을 인지하고 파이프라인을 바꾼 점이 의미 있다.

### 인증 보안

httpOnly Cookie + JWT로 프론트에 토큰을 노출하지 않았다. Bearer 호환은 남겨 API 테스트·Swagger 편의를 유지.

## 아쉬운 점

### KBO 파서 유지보수 부담

HTML/엔드포인트 구조 변경에 취약하다. 장애 시 seed fallback에 의존. 모니터링·알림이 없어 sync 실패를 늦게 발견할 수 있다.

### 단일 VM 한계

배포·DB·파일·cron이 한 서버에 몰려 있다. 트래픽·디스크가 늘면 수평 확장이 어렵다.

### UI 완성도

커스텀 CSS로 일관성은 확보했지만, 디자인 시스템·컴포넌트 라이브러리 없이 성장하면서 스타일 부채가 쌓인다.

### 푸시 알림 미구현

경기 알림·동행 알림이 앱 내부에만 머문다. PWA의 강점을 다 쓰지 못했다.

## 배운 것

| 주제 | 내용 |
|------|------|
| DB 설계 | 도메인(야구) + 과제(게시판) 테이블을 한 스키마에 녹이기 |
| 동기화 | upsert 키, 월 단위 API + KST 필터 |
| 프론트 | TanStack Query로 서버 상태, Zustand로 UI·세션 분리 |
| 보안 | rate limit, sanitize, httpOnly |
| DevOps | Docker Compose, Caddy TLS, GHA SSH 배포 |
