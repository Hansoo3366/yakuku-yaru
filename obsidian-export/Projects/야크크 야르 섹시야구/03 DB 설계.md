# DB 설계

스키마 원본: `apps/api/db/init/001_schema.sql`

## ERD 요약

```txt
teams 1 ── N users(favorite_team_id)
teams 1 ── N games(home_team_id / away_team_id)
teams 1 ── N players
players 1 ── 0..1 player_cheers

games 1 ── N attendance_records
games 1 ── N game_starting_pitchers
games 1 ── N game_lineups
games 1 ── N game_reminders

users 1 ── N posts
users 1 ── N comments
users 1 ── N attendance_records
users 1 ── N notifications
users N ── N attendance_records via attendance_companions

posts 1 ── N comments
players 1 ── N game_starting_pitchers
players 1 ── N game_lineups
```

## 도메인별 테이블 그룹

### 계정·인증

| 테이블 | 역할 |
|--------|------|
| `users` | 계정, 프로필, role, favorite_team_id |
| `email_verification_tokens` | 회원가입 인증 |
| `password_reset_tokens` | 비밀번호 재설정 |

### 야구 마스터·경기

| 테이블 | 역할 |
|--------|------|
| `teams` | KBO 10개 팀, 컬러, 예매 URL |
| `games` | 일정, 스코어, 상태, 취소 사유, external_id |
| `players` | 선수 마스터 (kbo_player_id) |
| `player_cheers` | 응원가 (1:1 with player) |
| `game_starting_pitchers` | 경기별 선발 투수·스탯 |
| `game_lineups` | 경기별 라인업 |

### 직관·알림

| 테이블 | 역할 |
|--------|------|
| `attendance_records` | 직관/집관 기록, 사진, 메모, 승패 |
| `attendance_companions` | 동행자 태그 상태 |
| `notifications` | 앱 내부 알림 |
| `game_reminders` | 경기 알림 on/off |

### 커뮤니티·구장

| 테이블 | 역할 |
|--------|------|
| `posts`, `comments` | 게시판 |
| `stadium_guides` | 구장 공통 맛집/주차 seed |
| `user_stadium_notes` | 사용자 개인 구장 메모 |

## 핵심 제약

```sql
-- 같은 경기에 사용자당 기록 1건
UNIQUE (user_id, game_id) on attendance_records

-- 동행자 1기록-1사용자 1행
UNIQUE (attendance_record_id, user_id) on attendance_companions

-- 경기 식별 (동기화 전 pending ID 대비)
UNIQUE (game_date, home_team_id, away_team_id) on games
UNIQUE external_id (nullable, KBO gameId)
```

## 왜 이렇게 설계했나

### 1. `teams`를 별도 마스터로 분리

- KBO 10팀은 고정·공유 데이터
- `users.favorite_team_id`, `games` 홈/원정, `players.team_id`가 모두 참조
- 팀 컬러·로고·예매 URL을 한 곳에서 관리

### 2. `games`와 KBO 동기화 식별자

KBO 공식 API가 없어 **external_id + external_source**로 upsert.

- 미래 일정은 `gameId`가 없을 수 있음 → `pending-YYYYMMDDhhmm-원정-홈` 임시 ID
- 실제 ID가 생기면 `(game_date, home, away)` 키로 **같은 경기 갱신**
- 스코어는 nullable (예정/취소/미동기화)

→ [[Decisions/KBO 크롤링 방식]]

### 3. 선수·선발·라인업 테이블 분리

- `players`: 선수 마스터 (주 1회 sync)
- `game_starting_pitchers`, `game_lineups`: 경기 단위 스냅샷
- 경기센터 데이터는 경기마다 덮어쓰기(upsert) — 시즌 통계와 분리

### 4. `attendance_records` 단순화

- 사용자가 스코어를 수정하지 않음 → `my_team_score`, `result`는 **동기화 스코어로 서버 계산**
- `is_score_modified`는 과거 호환 필드
- `last_modified_by_user_id`로 동행자 편집 추적

→ [[Decisions/공식 스코어 사용자 수정 불가]]

### 5. `attendance_companions` 분리 (N:M)

- 한 기록에 여러 동행자, 각자 수락/거절 상태
- **수락된 기록만** 동행자 캘린더·승률에 반영
- 호스트 기록과 동행자 뷰를 권한·상태로 분리

### 6. 알림 단일 테이블

- `type` enum: `attendance_tagged`, `companion_accepted`, `companion_rejected`, `post_commented`
- `actor_user_id`, 관련 `post_id` / `attendance_record_id`로 맥락 연결
- 푸시 없이 앱 내 폴링/조회로 처리

### 7. 파일은 DB에 저장하지 않음

- `photo_url`, `profile_image_url`만 VARCHAR
- 실제 파일은 API 서버 `/uploads` volume

## 인덱스 전략 (요지)

- FK 컬럼: `user_id`, `game_id`, `post_id` 등 조회용 KEY
- `games.game_date`: 캘린더 월별 조회
- `external_id`: KBO upsert
- `email`, `token`: unique
